\# ТЗ: Гибридный пайплайн оркестрации мультиагентной среды (Cloud-to-Local)

\#\# 1\. Концепция и цель  
Создание масштабируемой, модульной архитектуры агентного цикла (agent-loop), абстрагированной от конкретных названий LLM. Платформа работает как единый маршрутизатор (LLM Router), позволяя динамически подбирать оптимальную модель под конкретную задачу в моменте: от легких локальных моделей (для парсинга логов) до сверхмассивных опенсорс-решений (условно "100T параметров") или фронтирных облачных API (для сложной архитектуры).  
Стратегическая цель: постепенный уход от облачных вычислений в пользу полностью изолированной (air-gapped) локальной инфраструктуры по мере развертывания мощного оборудования и дообучения локальных моделей под специфику проекта.

\#\# 2\. Анализ исходной схемы (Self-Evolution Kernel)  
Схема описывает замкнутый цикл саморазвития пайплайна. Архитектура не привязывается к конкретным весам, а определяет роли:  
1\. \*\*Сбор данных (Observer):\*\* Узкоспециализированная локальная модель собирает баг\-репорты, телеметрию, скриншоты и логи. Данные векторизируются и сохраняются в локальную БД.  
2\. \*\*Формирование ТЗ (Architect):\*\* Использование наиболее мощной из доступных моделей (фронтирное API или массивная локальная LLM на серверном кластере) для анализа контекста и генерации формализованного ТЗ.  
3\. \*\*Реализация (Coder / Big LLM):\*\* Полный контекст передается в модель с высокими способностями к кодингу для написания и внедрения логики.  
4\. \*\*Ревью (Gatekeeper):\*\* Выделенная модель-ревьюер строго проверяет сгенерированный код на соответствие стандартам (protected\_paths.yaml) и политикам безопасности.  
5\. \*\*Финализация:\*\* Тесты, фиксы, сборка и деплой следующего цикла.

\#\# 3\. Матрица распределения ролей (Абстрактная модель)

| Этап пайплайна | Роль (Агент) | Приоритет развертывания | Требования к модели |  
| :--- | :--- | :--- | :--- |  
| \*\*Сбор телеметрии и RAG\*\* | \`Observer / Memory\` | Строго Локально | Высокая скорость инференса, поддержка мультимодальности (зрение для скриншотов). Низкие требования к reasoning. |  
| \*\*Анализ и написание ТЗ\*\* | \`Architect / Proposer\` | API \-\> Локально (Big LLM) | Максимальный уровень reasoning (сравнимый с 100T+ параметрами). Широкое контекстное окно для удержания архитектуры всего проекта. |  
| \*\*Написание кода\*\* | \`Coder\` | API \-\> Локально (Big LLM) | Специализация на кодогенерации (TypeScript, Python, G-code), поддержка вызова инструментов (FastMCP). |  
| \*\*Ревью и безопасность\*\* | \`Reviewer / Evaluator\` | Строго Локально | Строгое следование системному промпту (Gatekeeper). Способность выявлять архитектурные обходы. Часто дообучается (LoRA) на правилах конкретного проекта. |

\#\# 4\. Совместимость с репозиторием DentalAi (Анализ и интеграция)  
Интеграция данного пайплайна в текущую кодовую базу DentalAi требует соблюдения строгих архитектурных и нормативных рамок:

\*   \*\*Разграничение зон ответственности (MDR Compliance):\*\* Ядро саморазвития имеет право автономно модифицировать только \*\*Zone E\*\* (UI, оркестрация) \[cite: 6\]. Доступ моделей-разработчиков к \*\*Zone R\*\* (медицинская геометрия, генерация паспортов, CAM) и \*\*Zone P\*\* (политики) строго запрещен на уровне CI/CD и \`CODEOWNERS\` \[cite: 6\].  
\*   \*\*Исключение дублирования (FastMCP):\*\* В репозитории уже заложен протокол Model Context Protocol (FastMCP) для связи LLM с геометрическими алгоритмами \[cite: 7\]. Новый LLM Router должен нативно интегрироваться с этой шиной, а не создавать параллельную систему вызова функций.  
\*   \*\*Устранение блокеров (Phase 0):\*\* До запуска агентного цикла необходимо устранить критические баги, выявленные в аудите \[cite: 5, 6\]. Агенту \`Observer\` требуются реальные логи и данные, однако сейчас заказы хранятся в памяти (\`order\_service\`), лог аудита (\`AuditLog\`) не пишется, а QA-метрики генерируются случайно (\`np.random.randn()\`) \[cite: 5, 6\]. Цикл может быть запущен только после внедрения персистентности баз данных и реальной телеметрии.  
\*   \*\*Детерминированное ревью:\*\* Для исключения зацикливания ("Proposer \== Evaluator"), оценка полезности кода в Zone E (Evaluation) должна опираться не только на мнение LLM-ревьюера, но и на детерминированные скрипты (\`evaluator.py\`), анализирующие объективные метрики синтетических тестов \[cite: 6\].

\#\# 5\. Требования к LLM Роутеру  
Для обеспечения возможности "играться" моделями в моменте, ядро должно поддерживать:  
1\. Управление через единый конфигурационный файл (например, \`models.yaml\`), где каждой роли назначается текущий эндпоинт (OpenAI-совместимый API, локальный vLLM или Ollama).  
2\. Динамическое переключение (Hot-Swapping) моделей без перезапуска оркестратора \[cite: 7\].  
3\. Поддержку передачи специфического контекста через слэш-команды CLI или системные хуки платформы Antigravity 2.0 \[cite: 7\].
